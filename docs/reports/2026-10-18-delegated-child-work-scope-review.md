# Delegated child work: independent scope and delivery review

**Date:** 2026-10-18.
**Implementation baseline:** `25ef4657d2f1eda6e66b0282d09672cc053d6d89`.
**Target:** [delegated child work spec](../specs/delegated-child-work.md), especially its former D1-D9 sequence and issue splits.
**Method:** a fresh independent agent, without the earlier review conversation, inspected the spec, repository guidance and relevant current implementation. The reviewer made no edits and ran no tests. The author checked the implementation seams and incorporated the recommendations below into the spec's release plan. No Superpowers or issue dispatch was used.

The core is **parent delegation to ordinary multi-stage children, agent-created stacked PRs in multiple repositories, parent assessment and the configured final delivery boundary**. The draft still made this depend on a larger coordination product. The recommendation is to ship immutable required-child batches and incremental delegation first, retaining exact revisions, authority and recovery. Preserve the broader agreed behavior as later scope; remove unnecessary architectural prescriptions.

Value/complexity labels below are engineering judgments, not measured frequency or effort estimates. “Extremely high” means a clear operational benefit worth retaining even where a happy-path demo could omit it. “Uncertain” means the core does not establish enough benefit to justify the machinery yet. Complexity is incremental to today's implementation; a small configuration field can imply a large runtime change.

## What is essential

- Durable registration, deterministic child identity, ordinary pinned primary workflows, exact qualifying child results and one parent continuation. Preserve same-WorkItem watch semantics.
- One workflow-level delegation policy; inherit the invoking assignment's authority. Agents choose decomposition, workflow and ordinary Git/PR actions.
- Selected artifact references using existing grants, with a distinct immutable grant ID per child. Record exact join references rather than treating latest accepted publications as a frozen result.
- Explicit repository, checkout commit and logical PR base. Carry these through planning, implementation, review and PR verification; do not select the first available resource or follow a moving branch silently.
- Root WIP accounting, bounded child creation/execution, cancellation/freeze and inspectable failure. Waiting must release Run capacity; unrelated roots must still obey `maxOpenWorkItems`.
- Compare recorded consumed inputs and actual output/base/head revisions before acceptance or delivery. Stop on stale inputs; automatic repair is not required to make that stop safe.
- If automatic parent-controlled integration is enabled, use concrete owner-targeted activities. Preserve the child's PR ownership and approval/merge policy after its producing workflow has ended.
- Composed production-path proof, real Git fixtures and fake agents/providers, including restart and lost tool responses. Coverage belongs in each story, not only a final hardening story.

These are genuine changes. [Workspace selection](../../src/execution/application/execution-validation.ts) currently chooses a resource by kind precedence; [branch initialization](../../src/execution/infrastructure/workspace/git-workspace.ts) does not apply `checkoutRevision`. Existing [approval](../../src/activities/pr/approve.ts) and [merge](../../src/activities/pr/merge.ts) query authority for the invoking WorkItem. Existing [artifact grants](../../src/artifacts/application/artifact-context-service.ts) already provide selected directional sharing. Reuse those foundations rather than inventing replacement stores or authority systems.

## Recommended working process

1. Parent asks for the first required children in repositories A and B. Each child runs its ordinary plan/review/implement/code-review/PR workflow from a recorded base.
2. Each child finishes delivery-ready with an open PR. Wake records the exact successful results, then resumes the parent once.
3. Parent assesses those results and asks for the next children using the already completed upstream branch/head as explicit inputs. Agents create the next stack layer in each repository. This requires no waiting dependency DAG or early-output scheduling.
4. Parent records the current outputs and runs its configured assessment/QA. For a linear stack, its tip already contains earlier layers; separate assembly is needed only for independent changes the selected QA actually needs combined. Prepared checkouts and QA evidence refer to exact revisions. Agents handle product-specific assembly and testing.
5. A reviewed-PR-handoff workflow can finish at its declared boundary. A merge-required workflow must additionally perform owner-targeted, authorized integration and reconcile actual provider progress. Required retarget/review work remains agent activity. Stale or unsupported cases stop visibly; they cannot be counted as success.
6. Parent may request bounded repair as another ordinary assignment. Its accepted result explicitly replaces the affected contribution in the parent's current delivery selection; old assignment, join and PR ownership facts remain historical. This does not require a mutable general plan graph or a dedicated automatic correction engine.

Basic stacks mean dependent Git changes **within each repository**. Cross-repository coordination passes contract/result context; it never treats a commit from A as a Git base in B. A later queued-DAG release can reduce the parent's scheduling waves without changing this meaning.

The [spec's revised section 14](../specs/delegated-child-work.md#14-agreed-progressive-delivery-sequence) contains the concrete acceptance for these stories.

| C1: Durable child workflow invocation and join     | Ordinary pinned child workflows, immutable required-child batch, exact results and one parent continuation; existing artifact grants                    | None                                                        |
| C2: Reproducible repository-bound code children    | Ordinary multi-stage code/review workflow and one verified agent-created PR per child, in either authorized repo                                        | Agreed C1 assignment contract; can develop alongside C1     |
| C3: Agent interface and operating controls         | Workflow-level policy, submit/inspect, root WIP/Run/child limits, freeze/cancel and minimum failure/status visibility                                   | C1 contracts; can develop alongside C2                      |
| C4: Incremental stacks and exact parent assessment | Completed upstream outputs become next-batch bases; stacks in both repos; configured parent QA, conservative freshness and bounded further assignments  | C1-C3                                                       |
| C5: Configured post-result integration             | Concrete owner-targeted approve/merge and necessary agent retarget/review, preserving existing authority and delivery reconciliation                    | C2/C3 target facts; can develop alongside C4                |
| C6: First complete composed proof                  | Six children over two repos, intentional stacks, ordinary reviews, parent continuation/assessment, required final gates, recovery and one-slot behavior | C1-C4 for reviewed-PR handoff; C5 for automatic integration |

**First complete release:** C1-C6 for the configured delivery profile. C1's artifact-child fixture is an internal vertical proof, not a separately required product release. C2 and C3 proceed alongside it once contracts are agreed. C5 does not depend on general multi-output support, automated correction rounds or draft sharing. C6 does not wait for advanced dashboards.

There are two honest release endpoints: a declared **reviewed-PR handoff** (open PRs allowed), or **automatic integration** (C5 required). Recommend retaining C5 in the planned core so Wake's configured merge-required workflows have a usable path; the earlier handoff can be an explicit limited milestone. Neither endpoint permits bypassing configured QA or treating a merge-required parent as complete with open PRs.

Follow with independent enhancements: E1 parent clarification/attention automation; E2 queued dependency conditions and automatic stack refresh; E3 multi-output children; E4 recursion/optional children/general amendments; E5 draft recovery; E6 richer reporting; E7 cleanup. Existing typed application ports can later support static configured delegation if a real workflow needs it. Do not introduce separate supervisor, receipt or integration-progress services.

## Bounded independent re-review

The reviewer checked the revised C1-C6 scope and identified four narrow correctness clarifications, now incorporated without reinstating the held machinery:

1. Every original required assignment remains covered by an exact qualifying result or an authorized criteria-preserving replacement. Immutable replacement facts compare the expected current output; an arbitrary candidate artifact cannot waive requirements.
2. Targeted maintenance publishes a new immutable output/target revision with actual producer provenance. The parent's selection advances after required review/checks and affected configured QA; old child completion/join facts remain historical.
3. Unsuccessful batch continuation waits for all members to settle or be explicitly cancelled and reconciled. Still-blocked work remains visible for operator recovery; independent children continue. This avoids a hidden live attention lane and overlapping repair writers.
4. The supported automatic stack-integration profile must complete a positive merge-first-layer -> agent retarget/rebase -> publish exact facts -> refresh required review/QA -> restart -> finish remaining layers scenario. Merely stopping safely after the first merge is not a working automatic-integration endpoint.

Lower-stack replacement must also keep downstream outputs that consumed the old revision ineligible until explicit reassessment/replacement. A new child-owned replacement PR works at the handoff milestone without C5; updating a terminal child's existing PR needs C5's concrete maintenance capability. The per-delivery Run cap is a bound, not a fairness or capacity-reservation promise.

Subject to those clarifications, the independent re-review found no hidden prerequisite requiring live clarification routing, general dependency scheduling, multi-output children, draft sharing, specialized correction rounds or advanced dashboards before the complete core process.

## Limits

This review changes recommended implementation scope and sequencing, not production runtime behavior. It does not claim that fewer stories make cross-stream recovery or ownership enforcement easy. High-value optimizations remain subject to evidence from the working flow; complexity labels are qualitative rather than calendar estimates.

The earlier [correctness review](2026-10-18-delegated-child-work-review.md) remains useful. Its necessary facts survive: distinct grant IDs, failure visibility, owner-targeted actions, fetchable candidate inputs, no enabled wait cycles and explicit merge freshness. The recommendation removes richer first-release implementations of those facts where an existing mechanism or conservative stop is sufficient.

Documentation validation passed for UTF-8, local links/anchors, code fences, Markdown table structure, target acceptance IDs, C1-C6 headings, targeted Prettier formatting and `git diff --check`. Runtime tests were not rerun for these documentation-only scope changes.
